# Native conversation notifications

The React Native app obtains a device token from Apple or Google. Each installation can use its own Apple Developer and Firebase projects. Credentials stay on the worker. Expo Push Service, EAS and a central RIMIAM cloud account are optional for this flow. [Expo direct APNs/FCM guide](https://docs.expo.dev/push-notifications/sending-notifications-custom/)

## Enable for one platform

|         | Build the client                                                                                                                                                                                                                            | Set on API and worker                                                                                                                         | Set only on worker                                                                                                                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| iOS     | Enable Push Notifications in your explicit App ID and provisioning profile. Set `RIMIAM_MOBILE_APP_ID` to that bundle ID. Set `RIMIAM_IOS_APNS_ENVIRONMENT=production` for distribution or use the development default for a sandbox build. | `NATIVE_PUSH_ENABLED=true`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`, and `APNS_ENVIRONMENT=sandbox` or `production` matching the signed entitlement. | `APNS_KEY_ID` and the matching signing key in `APNS_PRIVATE_KEY`. Use a key scoped to the intended app and environment where available.                                                                                  |
| Android | Register your Android application ID in your Firebase project. Supply its matching client configuration using `RIMIAM_ANDROID_GOOGLE_SERVICES_FILE` when building.                                                                          | `NATIVE_PUSH_ENABLED=true` and `FCM_PROJECT_ID`.                                                                                              | Enable Firebase Cloud Messaging HTTP v1. Use a dedicated service account with permission `cloudmessaging.messages.create` for the target project. Provide `FCM_CLIENT_EMAIL` and `FCM_PRIVATE_KEY` from its credentials. |

Store private keys in the server secret store. PEM may contain actual newlines or escaped `\n`. Use the same stable application encryption secret on API and worker. Apply [migration 073](../../migrations/073_native_push.sql) before running these versions. Browser VAPID settings remain independent. If native push is disabled, the chat works and the panel reports unavailability. [Apple push authentication](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns), [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api)

## Verify on a phone

If the app shows an opt-in but no alerts arrive, compare the output of `npm run release:preflight` in the API and worker environments. Check `nativePushEnabled` and `variablesPresent` against the table above. The API knows the sender identity and subscription; the worker also needs its platform signing credentials. The report shows presence only. Successful delivery still needs a device test.

1. Install a signed build with the matching native configuration. Notification delivery on Android requires compatible Google Play services. Use two current, eligible accounts in the same Workspace.
2. From the Workspace tools on the recipient’s phone choose **Notifiche su questo telefono → Attiva per questo spazio** and grant permission. On Android the app creates the notification channel before asking. **Apri impostazioni del dispositivo** opens RIMIAM’s notification settings on compatible Android devices and falls back to app settings. On iOS it opens app settings. Return to RIMIAM to recheck. If the platform token check fails, the saved opt-in stays visible and can still be disabled.
3. Lock the phone. Have the second person send a message. Verify one generic RIMIAM alert. Tap it and check it opens the correct Workspace under the current session. The foreground app keeps the conversation quiet. Focus, Do Not Disturb, power restrictions and notification channel settings can silence presentation.
4. Repeat after opting out, ending membership and logging out. Test cold start, token expiration and return from settings on each platform. Record OS/build, actual alert visibility and destination.

The [native API](../../src/server/native-push.ts) records explicit opt-in per Workspace and session. The shared outbox rechecks eligibility at dispatch. Only generic title/body and opaque IDs go to the provider. A tap resolves its destination through authenticated API v1. Previously submitted OS notifications can still appear after a permission or membership change. They cannot open a revoked Workspace. The worker retries transient errors and retires explicitly unregistered tokens. A new session or token requires fresh opt-in in each desired Workspace. Receipt by APNs or FCM confirms handoff, not display.

On 2026-11-20, an iPhone 13 Pro simulator (iOS 18.2) granted notification permission through the system prompt and enabled one test Workspace through the app. A local test harness supplied a synthetic device token in place of APNs token issuance. XCTest tapped three iOS system alerts delivered through `simctl push`. Tapping the older top-level ID format with the app in the background opened the intended Workspace. Tapping the current nested `body` format after terminating the app opened the same Workspace. After the test account left the Workspace, tapping a previously queued notice launched the app into Home and the Workspace remained inaccessible. These checks exercised the production notification handling and authenticated target API on loopback. Physical-device registration, provider delivery and lock-screen presentation still need a signed build and a live device.

[Contract and transport tests](../../tests/native-push.test.ts) use real local authentication/PostgreSQL and generated signing keys, with deterministic HTTP provider responses. On 2026-11-20 an authenticated Android 15 emulator opened **Strumenti → Notifiche** against a local installation without FCM. The app explained that the operator must configure notifications and left opt-in unavailable. Delivery on a locked iPhone or Android phone still requires real provider credentials, device permission and a separate live check.

On the same Android emulator, tapping **Apri impostazioni del dispositivo** opened the system notification page for RIMIAM. Back returned to the Workspace notification panel. No permission was changed in this check.

## Lock-screen language

The native applications package the generic space-update notification in English and Italian. For a device that opted in with the localized build, APNs uses `loc-key` and FCM uses `body_loc_key`. The operating system chooses a bundled string when the app is closed and falls back to English for unsupported languages. The language selected inside RIMIAM controls its screens. Workspace names, senders and messages stay off the lock screen. [Firebase localization overview](https://firebase.google.com/docs/cloud-messaging/customize-messages/localize-messages) · [Apple notification payloads](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification)

Previously registered versions receive their existing generic Italian body. With the new binary and server, turning notifications off and back on in a space advertises support for localized alerts on that installation. Re-registering the same token and authenticated session preserves its other opt-ins and queued deliveries. Publish the compatible server and worker before distributing the updated native binaries.

The contract and transport regression runs against local PostgreSQL, generated signing keys and deterministic provider responses. It covers queued delivery across an upgrade and checks both provider payload formats. An isolated Expo prebuild generated both language resources, compiled with Apple's `xcstringstool` and Android's `aapt2`. Real lock-screen delivery still requires signed binaries, provider credentials, a physical device and that device's permission.
