# Google Calendar and Gmail

Calendar and Gmail follow [ADR-0011](../decisions/ADR-0011-calendar-stato-temporale-osservazioni-azioni.md) and [ADR-0012](../decisions/ADR-0012-workspace-email-privacy-bozze-invio.md). On 20 November 2026 the hosted beta enabled the Calendar API and provisioned separate sign-in and Calendar clients. Calendar is in external testing; individual consent and a real synchronization remain to be verified. Gmail activation is deferred. See the [deployment record](RAILWAY_DEPLOYMENT.md#current-setup).

## Self-hosting with Google

Create a Google Cloud project under your control for the installation. Set `BETTER_AUTH_URL` to the Web app’s HTTPS origin (HTTP loopback for local development). To offer Google sign-in and private integrations, create two **Web application** clients in Google Auth Platform. One handles identity. The other handles the enabled Calendar and Gmail grants separately. Replace `<origin>` below with that exact origin. Keep the credentials in your deployment’s server-side secret store and use separate projects for testing and production. The hosted beta’s credentials stay with its operator.

| OAuth client | Authorized redirect URI | Server configuration |
| --- | --- | --- |
| Account sign-in (identity only) | `<origin>/api/auth/callback/google` | Web: `GOOGLE_AUTH_CLIENT_ID`, `GOOGLE_AUTH_CLIENT_SECRET` |
| Calendar and/or Gmail | `<origin>/api/v1/integrations/google/callback` | Web and worker: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, and the same stable `BETTER_AUTH_SECRET`. Enable the corresponding Google APIs. Set `GOOGLE_OAUTH_CAPABILITIES` to `calendar`, `email`, or `calendar,email`. |

For **External → Testing**, sign-in requesting only `openid`, `email` and `profile` is available to Google accounts without adding them to a tester list, subject to account and organization restrictions. For Calendar or Gmail, add consenting accounts under **Audience → Test users**. Testers sign in first, then connect each capability from RIMIAM. Refresh tokens for these grants in testing normally expire after seven days. [Google audience and testing rules](https://support.google.com/cloud/answer/15549945).

For a **public installation**, use the operator’s verified domain, support contact, publicly accessible homepage and privacy notice. Link the notice from the homepage and the Google consent screen. It must describe how this installation accesses, uses, stores and shares Google data. Set `RIMIAM_PRIVACY_NOTICE_URL` to its HTTPS address. When ready, change the external app’s publishing status to **In production** and submit the Calendar scopes for Google’s sensitive-scope verification unless an exception applies. Publishing the source code and completing Google verification are independent steps. [Google verification requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification).

## Configuration and connection

For a Calendar-only activation, set `GOOGLE_OAUTH_CAPABILITIES=calendar` before adding credentials. Use `email` for Gmail only or `calendar,email` for both. Unset preserves historical installations. An empty or unrecognized value offers no new Google grants. The restriction applies before creating a request and during OAuth handoff and callback. It leaves existing connections, revocation, observations and history intact. Sign-in uses its own registration and ignores this setting.

After changing server settings, restart Web and worker. From a contributing account, open **Strumenti → Email → Le tue caselle**. **Non abilitato su questa installazione** means the grant is excluded by installation policy. **In attesa di configurazione dal gestore** means the capability is offered but the server configuration is incomplete. A ready button confirms local configuration only. Complete the controlled [mailbox verification](DEPLOY_EXTERNAL_SERVICES.md#caselle-personali-gmail-e-outlook) to establish real connectivity.

If overriding the integration callback with `GOOGLE_OAUTH_REDIRECT_URI`, register that exact URI. The existing `BETTER_AUTH_SECRET` derives a separate authenticated-encryption key. Keep OAuth launch/callback query strings out of logs. In Google Auth Platform → Data Access, declare the Gmail scopes listed below. Google classifies `gmail.readonly` as restricted and `gmail.send` as sensitive. For public use, server-side storage or transmission of restricted data generally also requires Google's security assessment unless the installation qualifies for an exception. [Scope classification](https://developers.google.com/workspace/gmail/api/auth/scopes). [Google restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).

`POST /api/v1/workspaces/{id}/google-connect` accepts `{capability: "calendar" | "email"}` with normal web CSRF/session or signed native authentication. It returns an expiring first-party `authorizationUrl`; open it in the system browser. Launch consumes a single-use ticket and sets an HttpOnly SameSite browser binding. Callback verifies state, PKCE, browser binding, current initiating session, membership version, eligibility, granted scopes and Google's verified identity. Connection creation, immutable connection history and final credential activation commit together. No project authority or effect authorization results from connecting.

The first supported Google connection requires its verified email to match the verified RIMIAM account email. This prevents a forwarded native launch link from attaching someone else's Google account to the initiator. This is a conservative implementation limit, not a product ban on additional owned mailboxes; a stronger authenticated account-linking ceremony is needed before supporting them.

`GET /api/v1/integrations/google/status` reports configuration availability only. Return to the app and refresh the existing Calendar/Email view after browser consent; no Google token or RIMIAM session token travels in a deep link.

## Credentials and boundaries

[OAuth handler](../../src/server/google-oauth.ts), [encrypted credentials](../../src/server/google-credentials.ts), [migration 015](../../migrations/015_google_integrations.sql). Tokens are encrypted with identity/purpose-bound AES-GCM; refresh uses a fenced, expiring claim and rechecks current membership/connection. Revoked eligibility, departed/re-entered membership and inactive connections cannot reuse a token. Existing disconnect commands atomically clear usable credential ciphertext. This local disconnection does not claim remote Google grant revocation, which can affect other connections and can be performed in the user's Google account settings. Auth-secret rotation requires reconnecting Google accounts.

OAuth handshakes expire after ten minutes. An interrupted exchange requires a new connection attempt; no partially created connection becomes active. Expired handshakes and orphaned connecting credentials are cleared when another connection is started. Private account, token, mailbox and Calendar observation data stay outside Shared Context.

## Supported adapters

- **Calendar:** `openid`, `userinfo.email`, `calendar.calendarlist.readonly` and either `calendar.events.owned.readonly` (personal Home) or `calendar.events.owned` (shared space with explicit publishing). Only calendars whose Google access role is `owner` are exposed. Bounded, paged events/availability; timed and all-day observations. Transparent events do not block availability. Stable operation-derived IDs for creates, ETag conditional patches for updates, no attendees or default reminders, suppressed update notifications. Unsupported recurrence/third-party/conference/reminder effects block modification. Only linked publications can be updated through existing domain commands. Network uncertainty stays unknown; matching operation/payload evidence can reconcile it, while absence cannot prove no effect.
- **Gmail:** `openid`, `userinfo.email`, `gmail.readonly`, `gmail.send`. Bounded search, message/thread and attachment reads; no mailbox modifications, drafts at provider, or inbox mirroring. Google's structured MIME payload is decoded locally using supported TextDecoder charsets. Private attachment bytes/hashes survive disclosure/send boundaries. Plain text is shown as text; an HTML-only message is shown as original HTML source without loading remote resources. Unsupported header/encoding/size structures fail explicitly rather than losing content. Search pages contain at most ten selected messages; threads over fifty messages require a narrower message request. These are operational read bounds, not retention limits.
- **Send:** exact approved envelope and attachment bytes become deterministic RFC5322/MIME. Reply retains the original Message-ID/references/thread; forward adds no implicit text/attachments. The existing Commit Point remains authoritative. A durable adapter dispatch record prohibits repeating an unknown send. Google acknowledgement gives a provider-acceptance receipt, not final delivery. Reconciliation requires a matching SENT message, Message-ID, exact envelope/content/attachment hashes and operation metadata. Missing or changed evidence stays unknown; a search miss never allows resend.

## Verification and remaining live work

[Tests](../../tests/google-integrations.test.ts) exercise the real adapters against deterministic HTTP boundaries and real isolated PostgreSQL: OAuth/session/CSRF/binding/replay/scopes, encrypted refresh/revocation, atomic finalization, Calendar ownership/preconditions/reconciliation, MIME bytes, Gmail uncertain dispatch and evidence-based receipt recovery. Existing Calendar/Email domain tests remain applicable. This is not evidence of real Google connectivity.

After credentials and user consent are available: connect a controlled same-email account independently for Calendar and Gmail; inspect exact granted capabilities; perform bounded private reads; explicitly approve one self-only Calendar create/update and one email to a controlled recipient; inspect real receipts, persistence and visible state; verify reconnect/disconnect and conditional-conflict handling. Unknown write outcomes must remain unknown unless the provider supplies sufficient evidence. Do not simulate a real-service pass.
