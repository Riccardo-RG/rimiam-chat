# Google Calendar and Gmail

Implemented adapter boundary, 2026-09-11. Semantics remain [ADR-0011](../decisions/ADR-0011-calendar-stato-temporale-osservazioni-azioni.md) and [ADR-0012](../decisions/ADR-0012-workspace-email-privacy-bozze-invio.md). **Real Google consent, credentials and service verification remain pending.** Test transport is injected only by tests; ordinary runtime never fabricates connections, observations or successful actions.

## Configuration and connection

Server-only environment names: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, optional `GOOGLE_OAUTH_REDIRECT_URI`. The redirect defaults to `{BETTER_AUTH_URL}/api/v1/integrations/google/callback`; register that exact web-application redirect in Google Cloud and enable Calendar/Gmail APIs. HTTPS is required except loopback development. Existing `BETTER_AUTH_SECRET` derives a separate authenticated-encryption key. Do not commit credentials or log OAuth launch/callback query strings.

Google project/consent configuration, allowed test users and actual user authorization are external prerequisites. Gmail read scope can require Google's restricted-scope review/security assessment for wider distribution. Development consent restrictions and Google token lifetimes must be checked before release, rather than inferred from local tests.

`POST /api/v1/workspaces/{id}/google-connect` accepts `{capability: "calendar" | "email"}` with normal web CSRF/session or signed native authentication. It returns an expiring first-party `authorizationUrl`; open it in the system browser. Launch consumes a single-use ticket and sets an HttpOnly SameSite browser binding. Callback verifies state, PKCE, browser binding, current initiating session, membership version, eligibility, granted scopes and Google's verified identity. Connection creation, immutable connection history and final credential activation commit together. No project authority or effect authorization results from connecting.

The first supported Google connection requires its verified email to match the verified MIRIAM account email. This prevents a forwarded native launch link from attaching someone else's Google account to the initiator. This is a conservative implementation limit, not a product ban on additional owned mailboxes; a stronger authenticated account-linking ceremony is needed before supporting them.

`GET /api/v1/integrations/google/status` reports configuration availability only. Return to the app and refresh the existing Calendar/Email view after browser consent; no Google token or MIRIAM session token travels in a deep link.

## Credentials and boundaries

[OAuth handler](../../src/server/google-oauth.ts), [encrypted credentials](../../src/server/google-credentials.ts), [migration 015](../../migrations/015_google_integrations.sql). Tokens are encrypted with identity/purpose-bound AES-GCM; refresh uses a fenced, expiring claim and rechecks current membership/connection. Revoked eligibility, departed/re-entered membership and inactive connections cannot reuse a token. Existing disconnect commands atomically clear usable credential ciphertext. This local disconnection does not claim remote Google grant revocation, which can affect other connections and can be performed in the user's Google account settings. Auth-secret rotation requires reconnecting Google accounts.

OAuth handshakes expire after ten minutes. An interrupted exchange requires a new connection attempt; no partially created connection becomes active. Expired handshakes and orphaned connecting credentials are cleared when another connection is started. Private account, token, mailbox and Calendar observation data stay outside Shared Context.

## Supported adapters

- **Calendar:** `openid`, `userinfo.email`, `calendar.calendarlist.readonly`, `calendar.events.owned`. Only calendars whose Google access role is `owner` are exposed. Bounded, paged events/availability; timed and all-day observations. Transparent events do not block availability. Stable operation-derived IDs for creates, ETag conditional patches for updates, no attendees or default reminders, suppressed update notifications. Unsupported recurrence/third-party/conference/reminder effects block modification. Only linked publications can be updated through existing domain commands. Network uncertainty stays unknown; matching operation/payload evidence can reconcile it, while absence cannot prove no effect.
- **Gmail:** `openid`, `userinfo.email`, `gmail.readonly`, `gmail.send`. Bounded search, message/thread and attachment reads; no mailbox modifications, drafts at provider, or inbox mirroring. Google's structured MIME payload is decoded locally using supported TextDecoder charsets. Private attachment bytes/hashes survive disclosure/send boundaries. Plain text is shown as text; an HTML-only message is shown as original HTML source without loading remote resources. Unsupported header/encoding/size structures fail explicitly rather than losing content. Search pages contain at most ten selected messages; threads over fifty messages require a narrower message request. These are operational read bounds, not retention limits.
- **Send:** exact approved envelope and attachment bytes become deterministic RFC5322/MIME. Reply retains the original Message-ID/references/thread; forward adds no implicit text/attachments. The existing Commit Point remains authoritative. A durable adapter dispatch record prohibits repeating an unknown send. Google acknowledgement gives a provider-acceptance receipt, not final delivery. Reconciliation requires a matching SENT message, Message-ID, exact envelope/content/attachment hashes and operation metadata. Missing or changed evidence stays unknown; a search miss never allows resend.

Existing Calendar/Email domain tests remain applicable. This is not evidence of real Google connectivity.

After credentials and user consent are available: connect a controlled same-email account independently for Calendar and Gmail; inspect exact granted capabilities; perform bounded private reads; explicitly approve one self-only Calendar create/update and one email to a controlled recipient; inspect real receipts, persistence and visible state; verify reconnect/disconnect and conditional-conflict handling. Unknown write outcomes must remain unknown unless the provider supplies sufficient evidence. Do not simulate a real-service pass.
